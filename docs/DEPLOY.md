# Публичный бэкенд

Кто это читает: тот, кто ставит Airena на свой сервер. Здесь только то, что
проверено на коде, — числа взяты замером, а не на глаз, и рядом с каждым
решением стоит причина, по которой другое решение сломало бы продукт.

---

## 1. Почему обычная машина, а не serverless

Выбор диктует не вкус, а четыре места в коде.

| Что | Где | Что из этого следует |
|---|---|---|
| Хранилище — `node:sqlite`, синхронный файл | `src/server/db.js` | нужен постоянный диск и один процесс-писатель |
| Цикл боёв крутит таймер, витрина считается сама | `src/server/arena-loop.js`, `src/server/app.js` | это синглтон с состоянием в памяти |
| Трансляция вещает на тридцати герцах, комнаты — в памяти процесса | `src/server/live.js` | долгоживущие сокеты, липкие к процессу |
| Чужой мозг исполняется в воркере-изоляте | `src/server/sandbox/index.js` | нужен настоящий Node и свободные ядра |

Лямбды, воркеры на краю и всё, что засыпает без запроса, отпадают целиком:
витрина обязана крутиться, даже когда никто не смотрит, — иначе первый гость
ждёт полный прогон боя вместо обещанного «уже идёт».

Генерация к машине не привязана: в продакшене она ходит по HTTPS к провайдеру
(`src/server/forge/llm.js`), а канал через локальный `claude` CLI без
`AIRENA_SUB_MODELS` в каталоге отсутствует вовсе. Хостить можно где угодно.

**Что берём: одну виртуалку с диском.** Вертикально, пока хватает.

## 2. Развёртывание

Нужен домен с A-записью на сервер и открытые порты восемьдесят и четыреста
сорок три — за сертификатом Caddy ходит сам.

```bash
# на сервере, под обычным пользователем в группе docker
git clone <репозиторий> airena && cd airena
cp .env.example .env
$EDITOR .env                      # домен, секрет, ключ провайдера, режим личности
docker compose up -d --build
docker compose logs -f airena     # сервер печатает режим одной строкой
```

Что должно быть в `.env` до первого запуска — см. сам `.env.example`, там у
каждой переменной написано, что она делает и чем платишь за неё. Секрет сессий
короче двадцати четырёх символов продакшен не примет: подписывать сессии
значением из исходников — это раздать всем возможность подделать любого игрока.

**Посев лестницы.** Свежая база пуста, а пустая база — это пустой пол вместо
витрины. Разово:

```bash
docker compose exec airena node tools/seed.mjs
```

Он стелет лестницу из популяций в `brains/` (они в образе) и заодно меряет,
какие пары слабы настолько, чтобы ставить их новичку в спарринг.

**Проверка:**

```bash
curl -s https://<домен>/api/health
```

## 3. Личность игрока

Личность даёт платформа: `embedToken`, подписанный её ключом. Подпись
проверяется по-настоящему — `src/server/identity.js`.

**Что прочитано на стенде, а не додумано** (E8): платформа проверяет свой токен
по паре `aud === 'embed'` и `scope === 'embed:play'`, билет сессией не считает
(`genex-demo/apps/api/src/embed/verify.ts`); в токен кладутся `sub`, `sid`,
`slug`, `projectId`, `name`, `channel`, а у гостевого — ещё `guest: true` и
`sub` вида `guest:<uuid>` (`embed/routes.ts`); срок жизни пятнадцать минут,
подпись плагином с ключами из открытого набора (`auth.ts`). Набор проверен на
живой платформе: `EdDSA` на кривой `Ed25519`, а такую подпись читает штатный
`node:crypto` — ни одной новой зависимости.

**Сверка игры обязательна, и без неё сервер не встаёт.** Токен выписан для
одной игры. Сервер, который проверил подпись и не сверил `slug`, принимает
токен любой игры платформы: чужая игра выписывает своему игроку валидную
подпись, тот приносит её сюда и заводит аккаунт. Поэтому `AIRENA_GENEX_SLUG`
(или `AIRENA_GENEX_PROJECT`) — обязательная переменная, а не удобная. Слаг
показывает `npx genex list`.

**Гость платформы аккаунтом не становится.** У гостевого токена `sub` новый на
каждую сессию. Пустить его в стену аккаунта — это по аккаунту на каждое
открытие страницы, с сожжённым пожизненным бесплатным существом (F7) и
лестницей из одноразовых владельцев. Гость платформы остаётся гостем Airena.

**Чего нет.** `iss` по умолчанию не проверяется: настоящего токена в руках не
было, а `iss` — это адрес продакшена платформы, которого в стенде нет. E8
запрещает выдавать дефолт чужого кода за факт продакшена, поэтому проверка
написана, но включается переменной. Якорь доверия при этом не пропадает — им
остаётся адрес набора ключей по TLS.

**Гейт** — `tools/checkidentity.mjs`, в наборе `npm test`. Двадцать одна
проверка: четырнадцать подделок против модуля и пять против живого
продакшен-сервера, потому что модуль может быть безупречен, а маршрут — забыть
его дождаться. Ключи там свои, поднятые на localhost: гейт меряет нашу
проверку, а не доступность платформы.

**Вторая половина — на клиенте, и она была сломана иначе.** Страница брала
токен своим выдуманным обменом: слала родителю `genex:requestEmbedToken` и ждала
`genex:embedToken`. Ни одного из этих сообщений в протоколе платформы не
существует, то есть внутри настоящего фрейма стена не получила бы токен никогда,
а серверная проверка осталась бы недостижимой. Настоящий обмен: игра шлёт
`genex:embed:ready`, родитель отвечает БИЛЕТОМ, игра меняет билет на токен через
`POST /api/embed/session`, и источник сообщения сверяется со списком доверенных.
Теперь это делает SDK самой платформы (`@genex-ai/embed-sdk`), подключённый тем
же приёмом, что three.js: маунт на `node_modules`, запись в карте импортов,
динамический импорт — чтобы вес не лёг на путь до первого кадра (F6).

Проверено полным кругом на стенде: поддельный дашборд выдал билет, SDK обменял
его на подписанный токен у поддельной платформы, бэкенд в НАСТОЯЩЕМ
продакшен-режиме проверил подпись и завёл аккаунт `genex_sub: user_…`,
`is_guest: 0`. Гостевая ветка проверена там же: платформа отвечает «гость» —
стена говорит «войди в аккаунт платформы», аккаунт не заводится.

**Превью — это тестовый канал, и это меняет две настройки.** Замерено на живом
превью: воркер впрыскивает `channel: "staging"`, то есть там тестовые ВСЕ
токены, а по умолчанию мы их отвергаем (тестовая сборка не пишет в живой
рейтинг). Для превью-стенда со своей базой это снимается `AIRENA_ACCEPT_STAGING`.
Второе: превью живёт на `preview--<slug>.genex.technology`, а опубликованная
игра — на `<slug>.genex.technology`; это разные источники, и в `AIRENA_CORS`
нужны оба.

И третье, чего не ждёшь: **черновик не открывается по прямой ссылке**. Заход на
адрес превью посторонним отбивается через `/play/authorize` страницей «This game
isn't available» — черновик виден только своему владельцу и только из дашборда,
`https://genex.games/draft/<slug>`. Это не поломка, а как устроен черновик.

**Аварийный режим остаётся.** `AIRENA_ALLOW_NO_IDENTITY` поднимает сервер
витриной: бои идут, смотреть можно, аккаунт завести нельзя. Он нужен, только
пока игра на платформе не заведена или платформа недоступна.

## 4. Диск

Замерено на рабочей базе: **сто двадцать тысяч матчей — семьсот тридцать шесть
мегабайт**, то есть около пяти килобайт на бой (`result_json` и `kits_json` —
почти весь объём). Правила удаления старых матчей в продукте **нет**: база
растёт линейно с числом боёв, включая витринные, которые идут постоянно.

При цели «десять матчей на активного игрока в день» из §14 тысяча активных —
это порядка полутора гигабайт в месяц. Восьмидесяти гигабайт хватает надолго,
но правило удаления придётся написать раньше, чем кончится диск.

**Бэкап** — `tools/backup.mjs`, снимок через `VACUUM INTO` на живом сервере.
Обычным `cp` базу в режиме WAL копировать нельзя: свежие страницы лежат в
`-wal`, и копия выйдет либо без последних матчей, либо битой. Замер: семьсот
девять мегабайт за четыре секунды, `integrity_check` — `ok`.

```bash
# в cron, ежедневно
docker compose exec -T airena node tools/backup.mjs --out=/data/backup --keep=7
```

Снимки лежат на том же томе — это защита от ошибки в коде, но не от смерти
диска. Увозить их с машины (снапшот провайдера, объектное хранилище) —
отдельный шаг, и он обязателен: пожизненно бесплатное существо игрока
невосстановимо (F7).

## 5. Куда это масштабируется

Узкое место — не сервер, а синглтон. Порядок, в котором его придётся резать:

1. **Матч из главного процесса в пул воркеров.** Пул уже есть — для мозга.
   Сегодня прогон боя блокирует тридцатигерцовую трансляцию, и это видно уже на
   одной машине.
2. **Цикл боёв и трансляцию — в отдельный сервис**, а API оставить без
   состояния. Только после этого вторая реплика вообще имеет смысл. A3 этого
   всё равно требует: результат, влияющий на рейтинг, пересчитывается сервером
   из сида.
3. **`node:sqlite` → внешняя БД.** `src/server/db.js` — одна дверь, менять там.
4. **Очередь генераций** (`src/server/jobs.js`) уже отделена — её увести в
   свой процесс проще всего.

И то, что упрётся раньше железа: **деньги на генерацию**. Симуляция стоит
копейки — бой это семьдесят миллисекунд процессора, — а пара мозгов стоит
доллар, и §14 требует держаться в тридцати центах на игрока в месяц. Потолок
здесь денежный, а не вычислительный.
